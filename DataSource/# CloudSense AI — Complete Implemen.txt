For DoW, keep two tasks separate: Isolation Forest is your primary unsupervised detector, as specified in your abstract, while labeled attack data is used to assess its detection quality and compare it with alternative detectors.

### How to obtain meaningful labels

Real attack labels are the hardest part. Do not label every high CPU or high-cost period as an attack.

Use three categories:

- `normal`: normal workloads and ordinary cost variations.
- `operational_anomaly`: unusual but not confirmed malicious behavior.
- `dow_candidate` or `dow_confirmed`: simulated attack windows or incidents supported by the dataset's labels and methodology.

A synthetic DoW generator can create controlled bursts in invocation rate, provisioning frequency and cost velocity. Mark these as simulated data, preserve the random seed and document the attack-generation assumptions. Evaluate synthetic results separately from public labeled results.

For Unit Economics, you also need business KPIs. Your own application can generate safe sample values for active users, API requests and transactions. If you lack real business telemetry, use a clearly identified synthetic dataset rather than pretending those figures came from AWS.

Purpose: predict future AWS expenditure.

Input: daily aggregated cost per account, service, or resource group.

Input dataset format

| ------------------- | ----------------------------------------------- |
| `ds`                | `2026-10-01`                                    |
| `y`                 | `125.60`                                        |

Initial parameters

- `growth`: `linear`
- `daily_seasonality`: `False` for daily aggregated data
- `weekly_seasonality`: `True` when supported by the history
- `yearly_seasonality`: `auto`, depending on history length
- `interval_width`: `0.80` for an initial prediction interval
- `horizon`: 7, 30 and 90 days for different forecasts

Training process

1. Aggregate billing data by day and define whether the target is net amortized cost, unblended cost or another consistent cost basis.
2. Fill or investigate missing dates; do not treat missing billing records as zero without checking why.
3. Train Prophet on earlier dates only.
4. Forecast the next 7, 30 and 90 days.
5. Compare predictions against future actual cost using rolling-origin validation.
6. Display forecast intervals and the expected budget-overrun date when one can be calculated.

Evaluation: MAPE and RMSE, as specified in your paper. Add MAE to make absolute dollar errors easier to interpret.

A MAPE target below 5% is your research target, not an assumed outcome.

### Model C — Isolation Forest: anomalies and DoW signals

[IsolationForest example — scikit-learn 0.21.3 documentation](https://images.openai.com/static-rsc-4/vTl66T3ysA0Hco1xkBotB5TSUmnoVoIa4WttL7ouFRfHfzNGchJBtZH6d_YXiCHT3AtuzC3JYWQQZ_LYgVZmGWcCU-vOUlQYoqZvvAqhaczW7B5yKJ3SLKArdp5YPPFpsEN4GtzSERPPlNNAJOStyLGgylS3TPuSFm7C7hX6maA?purpose=inline)

Purpose: flag unusual infrastructure or spending behavior without requiring every event to be labeled.

Input: time-aligned operational metrics and engineered change features.

Features

- `cost_velocity`
- `request_rate`
- `request_rate_delta`
- `provisioning_frequency`
- `cpu_utilization`
- `network_io`
- `storage_growth_rate`
- `spend_vs_baseline`
- `invocation_rate`, where applicable

Your paper defines two key engineered features:

\\[ \text{CostVelocity}(t)= \frac{\text{Cost}(t)-\text{Cost}(t-\Delta)}{\Delta} \\]

\\[ \text{ProvisioningFrequency}(t)= \frac{N\_{\text{create}}(t)}{|t|} \\]

Implement both with clearly defined units and time windows.

Initial parameters

- `n_estimators`: 200
- `contamination`: `0.01` as an initial experimental assumption
- `max_samples`: `auto`
- `random_state`: 42

`contamination=0.01` does not mean 1% of events are actually attacks. It is an initial setting that influences the model's outlier threshold; tune it against validation results and operational alert volume.

Training process

1. Build fixed-interval time buckets, such as 5-minute windows.
2. Calculate the cost and provisioning rates and their changes.
3. Fit the model on representative historical normal or predominantly normal data.
4. Generate anomaly scores for later observations.
5. Tune the alert threshold using labeled anomaly windows and simulated attack scenarios.
6. Group consecutive anomalous windows into incidents and attach supporting metrics.

Evaluation: precision, recall, F1-score and AUPRC. Measure false positives, detection delay and alert volume as well.

Do not directly interpret an Isolation Forest score as a calibrated probability that an attack occurred. A score threshold can produce an alert, but a trustworthy confidence probability needs a separately justified calibration process.

### Model D — SHAP: explain the prediction

SHAP is the explanation layer, not a fourth predictive model.

For XGBoost, use `TreeExplainer` to show which features influence a prediction. For example:

- Cost per request is rising.
- API requests are stable.
- Provisioning frequency has increased.
- Network traffic does not explain the increase.

That evidence can be converted into a readable explanation, with a risk level and recommended next investigation. For Isolation Forest, your paper mentions Kernel SHAP; use a carefully chosen sample because general-purpose explanations can be expensive.

Estimated savings must come from a separate calculation. Estimate the baseline and optimized cost, validate the assumptions, and show the expected range. SHAP feature importance alone does not establish financial savings.

## 6. How to train the models from start to finish

Follow this sequence rather than training all three models at once.

1. Create the data collection layer

   Implement Python collectors for CUR files in S3, CloudWatch metrics, resource inventory and your KPI data. Store raw records before transforming them so you can reproduce your experiments.
2. Create a common data schema

   Standardize timestamps to UTC, use consistent currency units, preserve AWS account and resource identifiers, and document the aggregation interval. Save a data dictionary alongside the datasets.
3. Build separate training datasets
   - `cost_daily.csv` for Prophet.
   - `unit_economics.csv` for XGBoost.
   - `anomaly_windows.csv` for Isolation Forest and anomaly evaluation.
   Use `dow_labels.csv` for labeled DoW evaluation and keep synthetic labels distinguishable from observed labels.
4. Perform data quality checks

   Inspect missing timestamps, duplicate rows, impossible negative counters, missing KPI values, outliers and billing revisions. Check that cost and KPI values use the same reporting period.
5. Train and evaluate each model independently

   Establish simple baselines first. Use an initial chronological split with the earliest 70% for training, as proposed in your paper, then evaluate on later periods. Use expanding-window rolling-origin validation for time-series experiments.
6. Add XAI and the recommendation engine

   Combine predictions with feature attributions, cost estimates, risk policies and resource metadata. Each recommendation should explain why it exists and what evidence would justify the proposed action.
7. Version and persist model artifacts

   Save the trained model, feature schema, training-data version, hyperparameters, evaluation metrics and training timestamp. Use MLflow to track experiments and store approved model artifacts in S3.
8. Integrate with FastAPI

   Load approved artifacts, expose prediction endpoints and store results in PostgreSQL. The API should return structured JSON, not raw notebook output.
9. Run shadow monitoring before remediation

   Compare predictions and recommendations with actual outcomes without changing AWS resources. Once the behavior is validated, introduce the approval-controlled remediation workflow.

## 7. Accounts, API keys and credentials you need

You need AWS access for cloud integration, optional credentials for notifications, and optionally an LLM provider for the conversational assistant. You do not need an API key for every model or Python library.

1\. AWS account

Required for live cloud data and AWS remediation. Enable MFA, establish a budget alert, choose a region, and create a dedicated development environment. Billing access and the permissions needed to read resource metrics must be configured separately.

2\. IAM role or user credentials

Use temporary credentials or an IAM role wherever possible. Give the data collector read-only access to the resources it needs, and give the remediation service a separate, narrowly scoped permission set.

Never embed AWS access keys in frontend code, source files, Git repositories or prompts to AI coding tools.

3\. Slack, Teams, Discord or email credentials

Configure only the notification channels you actually use. A Discord webhook or Slack webhook can be enough for a prototype. Email delivery may require provider configuration and verified sender details. Store webhook URLs and other secrets securely.

4\. Optional LLM provider API key

If your conversational assistant uses a hosted LLM, create a provider account and API key for that provider. The key is only required for that integration; it is not required to train Prophet, XGBoost or Isolation Forest.

You can first build the dashboard and deterministic recommendation APIs without an LLM.

5\. PostgreSQL and local development tools

Install Python, Node.js, Git, Docker, PostgreSQL and VS Code. Your approved project specification lists FastAPI, React, Tailwind CSS, TypeScript, SQLAlchemy, Pydantic, scikit-learn, XGBoost, Prophet, SHAP, LangChain, LangGraph and Boto3.&#x20;

## 10. How MCP, Boto3 and LangGraph fit together

These technologies serve different purposes:

LangGraph / conversational assistant

Interprets the user's request, gathers context, calls permitted tools and presents the results. It should not be the security authority for executing cloud changes.

MCP client and server

Provide structured tool discovery and communication, such as `list_resources`, `get_cost_metrics`, `preview_action` and `execute_approved_action`. The server enforces which tools and operations are permitted.

Boto3 execution layer

Calls the actual AWS APIs using the configured AWS identity. It performs the action only after server-side authorization, approval verification and parameter validation.

For example, the assistant might identify an EC2 instance as a possible optimization candidate. It should first retrieve its utilization history and dependencies, estimate potential savings, and create a recommendation. An authorized user reviews the recommendation, and the server validates the exact approved action before calling Boto3.

Your paper specifies this human-in-the-loop workflow rather than unrestricted autonomous changes. Preserve that requirement throughout implementation.&#x20;
